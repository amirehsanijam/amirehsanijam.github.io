# Bonice group orders

A responsive Persian group-order page for Bonice (Jordan / Elahiyeh). It includes a searchable menu, individual baskets, shared totals, CSV export, and private edit/delete links. The 175-item menu is a snapshot from 4 November 2026; prices and availability may change. This page collects orders for a coordinator and does not purchase from Snappfood.

## Hosting

The complete application source belongs in this GitHub repository. GitHub Pages hosts the frontend. Shared orders remain in the existing Railway service, using SQLite on a persistent `/data` volume. GitHub Pages is static hosting and cannot run the order API or a writable shared database.

Existing backend: https://bonice-group-production.up.railway.app

No live order database, personal order snapshots, or private order-management credentials belong in this repository. Keep the Railway service and volume while shared orders are in use; its ongoing availability depends on the Railway account's hosting plan.

## Development

Use Node.js 24 and npm:

```sh
npm ci
npm run dev
```

The development server starts a local SQLite database in the ignored `.sites-runtime/` directory. To produce and check a standalone build:

```sh
npm run build
npm test
node server.mjs
```

The HTML output is `dist/client/index.html`. The same build also preserves the original Sites worker outputs for portability. `server.mjs` serves the standalone HTML and API; set `HOST=0.0.0.0` only when remote access to that server is intended.

## GitHub Pages

The workflow in `.github/workflows/pages.yml` builds, tests, and publishes on pushes to `main`. Set the repository's Pages publishing source to **GitHub Actions**. It discovers the site's base path, so both an account site and a project site work.

The workflow uses the current Railway API by default. To use another backend, set the GitHub repository variable `API_BASE_URL` to its HTTPS origin. On that backend set `ALLOWED_ORIGINS` to the exact Pages origin (for example `https://YOUR-ACCOUNT.github.io`, without a project path). Multiple allowed origins can be comma separated. Unconfigured origins are rejected; order writes still require the private owner token.

Build-time frontend settings:

| Variable | Purpose |
| --- | --- |
| `VITE_API_BASE_URL` | Shared API origin. Empty means same origin, for the Railway or local full app. |
| `VITE_BASE_PATH` | Website path, such as `/bonice-group/`. Pages supplies this automatically. |
| `VITE_PUBLIC_SITE_URL` | Canonical new frontend URL. Set this when rebuilding the old Railway page after migration. Leave empty for the Pages build. |

## Existing orders and private access

Browser storage belongs to each website origin. After the new site is live, rebuild the Railway page with `VITE_PUBLIC_SITE_URL` set to the Pages URL. A visible button opens the new site and transfers only the current browser's active owned-order keys through the URL fragment. The new site imports them and immediately removes the fragment. The keys are never added to query parameters or the shared order API response. Private links copied on the old site also point to the new address.

Keep private management links to yourself. Names and order contents are visible to people with the group link; management keys authorize edits and deletion. Visitors without a key cannot change that order.

## Railway runtime

The currently deployed app uses the self-contained Bun Function generated by:

```sh
npm run build
npm run build:railway
```

Deploy the complete `railway/function.ts` through Railway. It requires `ORDER_DATA_DIRECTORY=/data`, an attached persistent volume at `/data`, and the configured `ALLOWED_ORIGINS` for a separate frontend. The generator enforces Railway's 96 KiB source limit. Keep one replica for this SQLite database.

`Dockerfile` is an alternative Node deployment; run the build before building the container. Local and production databases are initialized only when the schema is absent. Redeploys must reuse the existing volume; do not restore old test snapshots over live orders.
